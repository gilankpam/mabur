# 40 MHz (HT40) — as built

Measurements behind the design: `docs/findings/2026-09-23-bw40-sweep.md`
(the eight facts, range per width/MCS). Bench of the 40 MHz rungs:
`docs/findings/2026-09-24-bw40-rungs-bench.md`. Design: spec
2026-09-24-bw40-design (gitignored, local only). The channel set itself and
the pick are [`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md); this page covers width and offset.

## What flies

- GS: no `radio.width` key — the receiver width is derived from `[link]`
  (`derived_width`, [`gs/src/config.h`](https://github.com/gilankpam/mabur-ground/blob/master/gs/src/config.h): `static_bw` under a fixed pin, else
  40 iff any `[[link.ladder]]` rung has `bw = 40`, else 20). Every link
  card tunes to that derived width, HT40 on the current channel's
  standard pair when it is 40 — every member of the channel set shares one
  `ht40_offset` ([`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md) "Config"; e.g. member 144 →
  140+144, primary = the upper half). A 20-tuned receiver cannot hear
  HT40; a 40-tuned one hears 20 MHz frames on the primary for ~0.2-1 dB. A
  live ladder/`static_mcs`/`static_bw` set that moves the derived width
  retunes every ready card first ([`docs/gs-live-config.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/gs-live-config.md) "Width flip").
- Drone: `radio.width = 40`, InitWrite on its start channel's pair (the
  remembered member, else the first, [`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md) "Drone
  behaviour"); airs EACH RUNG at the width the RCF profile byte names
  (`LayerTxSpec.bw`). The drone's own `radio.width` is independent of the
  GS's derived width and stays 40.
- Ladder ([`gs/bundle/maburgs.default.toml`](https://github.com/gilankpam/mabur-ground/blob/master/gs/bundle/maburgs.default.toml)): six rungs, MCS 0-5, all
  `bw = 20`, so the GS derives width 20 out of the box; loading a ladder
  with a `bw = 40` rung (the goggles menu's Width row loads the five-rung
  MCS 0-4 `bw = 40` ladder) or pinning `static_bw = 40` flips the derived
  width to 40 — no separate width key to edit. Per-rung width is free
  (`[[link.ladder]] bw` is 20 or 40), but the GS config refuses a 40 rung
  or `link.static_bw = 40` unless the channel set is 40 MHz pair-valid
  (`radio_width_issue`, [`gs/src/config.cpp`](https://github.com/gilankpam/mabur-ground/blob/master/gs/src/config.cpp)); reshaping the ladder is a
  config edit. Trade-off from the range test: HT40 MCS3 reaches 1-1.6 dB
  further than HT20 MCS5 at more capacity, but HT40 MCS0 reaches 4-6 dB
  less than HT20 MCS0.
- Bitrate cap 24 Mb/s (drone `encoder.bitrate_max_kbps`): the 40 rungs buy airtime,
  not bitrate.
- Control and telemetry frames are pinned to MCS0 / 20 MHz / STBC, LDPC per
  `radio.ldpc`, with `TxMode::no_agg` (`drone/src/control_tx_mode.h`). The
  probe canary is different: it flies the PROBE RUNG's own `(mcs, bw)` —
  `to_tx_mode(*probe, probe->bw)` — and shares only `no_agg` with
  control/telemetry (`drone/src/radio_tx.cpp`'s probe layer), so it
  measures the NEXT rung at that rung's own width. `no_agg` keeps every one
  of these frames a PPDU of its own, so an A-MPDU session never folds them
  into a video aggregate at the aggregate's rate/width. Video layers
  aggregate per `ampdu.min_mcs_20/_40`.
- Static pin: `link.static_mcs` + `link.static_bw` (40 needs the GS's
  channel set to be 40 MHz pair-valid; there is no `radio.width` key on
  the GS to also set).

## Per-width tables (drone)

Everything the drone prices or parks on has a table per width, picked by
the rung's `bw`:

- **TX-power walls**: `radio.rate_walls_rel_20` / `_40` (with
  `cal_flags_20` / `_40`, the coding flags each was measured under).
  `maburd` keeps one plan per width and programs the applied rung's on
  every rung change — the chip's per-rate diff table has no width axis, so
  one table is live at a time (`maburd radio: power table 40 MHz live
  (mcs5 diff N)` on each switch). A width with no table of its own flies
  the other width's, logged at boot (`maburd radio: no 40 MHz walls,
  flying the 20 MHz table at 40`). Control frames ride the one
  `legacy_wall_rel`. `docs/calibration.md` "Per-width tables on the
  drone".
- **Air capacity**: `air_clock.efficiency_20/_40` (delivered/nominal per
  MCS), measured per unit by `maburcal`'s capacity sweeps and read at
  `maburd` start; the bundle carries the reference unit's 20 MHz `[0.93,
  0.88, 0.84, 0.80, 0.76, 0.76, 0.78, 0.76]` and 40 MHz `[0.77, 0.75,
  0.75, 0.75, 0.74, 0.77, 0.76, 0.75]`. `delivered_mbps`
  (`drone/src/air_rate.h`) picks by `bw`.
- **Aggregation**: `ampdu.min_mcs_20 = 4` / `min_mcs_40 = 2`;
  `ampdu_mode_for` (`drone/src/ampdu_policy.h`) picks by `bw`.

The wall and efficiency keys and `min_mcs_20/_40` are optional in the
drone config: an absent efficiency defaults to nominal (1.0 per MCS), an
absent `min_mcs` to 0, an absent wall table to the other width's (and
`power_mode = "offset"` needs at least one). The bundle sets them all
(`tests/test_config.cpp`'s `bundle_default_sets_every_known_key` keeps
every key present; the values are per-unit or tuning and deliberately not
pinned).

## Channels: one offset for the whole set

FastRetune keeps width AND offset on both ends, so every member of the
channel set ([`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md)) must sit on the same side of the
40 MHz pair grid. Rule (`common/include/mabur/channel_set.h`'s
`channel_set_issue()`, enforced by both the GS's and the drone's config
load at `width = 40`): **every member is a standard HT40 pair primary and
all members share one `ht40_offset`.** The GS's and the drone's lists must
also match (the drone's may be a superset); no loader can check that across
devices, so it is an operator rule ([`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md) "Config").

Which pairs are worth flying: 116+120, 149+153, 157+161 (and 52+56,
100+104) are 8822E spur centres (65-91 ms retunes); 165 has no pair.
Devourer's `fast_retune` declines only spur centres and band changes. That
leaves seven spur-free pairs: 36+40, 44+48, 60+64, 108+112, 124+128,
132+136, 140+144. The default set `[40, 64, 112, 144]` takes four of them:

- 140+144 (primary 144, 5690-5730).
- 108+112 (primary 112, 5530-5570): the 5.25-5.6 GHz DFS block, clear of
  every FPV system — analog/HDZero raceband (5645-5945; 132+136 holds
  R1/E2/E3, 140+144 R2/E1/A8), DJI O4 (5725-5850, and 5170-5250 where
  enabled), Walksnail (5.8). The scout reads an analog carrier as silence
  (`docs/findings/2026-09-25-analog-vtx.md`) and never decodes DJI, so
  spectral distance is the defence, not measurement.
- 36+40 (primary 40, 5170-5210): DJI O4's 5.1 GHz band where enabled;
  treat that as a live caveat on 40.
- 60+64 (primary 64, 5290-5330): provisional — see
  [`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md) "Open items" (row 8).

Left out: 132+136 (analog raceband R1/E2/E3), 44+48 (adjacent to 36+40)
and 124+128 (E4 5645 at its edge; 5600-5650 is the weather-radar block;
128 is the fallback if 64 fails). How the list got here:
`docs/findings/2026-09-26-bw40-channel-candidates.md`.

## Boot scan dwells once per pair

The boot scout card is opened at the derived receiver width like every
other card ([`gs/src/main.cpp`](https://github.com/gilankpam/mabur-ground/blob/master/gs/src/main.cpp); the web GS likewise), and the scout itself
never switches it. Only a live width flip retunes it ([`docs/gs-live-config.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/gs-live-config.md)
"Width flip"), once the scout has let go of the card; its later dwells run
at the new width. At 40 MHz
it dwells once per pair, on the member itself — the pair's primary — so
for the default `[40, 64, 112, 144]` a round is four dwells. One dwell
reads:

- **NHM busy % over the whole pair.** A 40-tuned card's busy-airtime
  window covers both halves, so the reading is the max of the halves by
  construction: secondary-only traffic reads within 0.5 points of a
  20 MHz dwell on that half
  (`docs/findings/2026-11-03-ht40-dwell-secondary.md`).
- **Frame terms (FA, CCA, decoded foreign), primary-biased.** A
  secondary frame is never decoded at 40 MHz, and FA/CCA respond to
  secondary traffic more weakly than to primary traffic.

The search burst is unchanged: DISC on the primary, sent as 20 MHz frames
from the 40-tuned card, which the drone hears on its primary.

The ranker keeps one row per member (`ChannelRanker` over
`radio.channels`), and the pair pick reads it NHM-first
(`pair_proposal`, [`gs/src/pair_pick.h`](https://github.com/gilankpam/mabur-ground/blob/master/gs/src/pair_pick.h); [`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md) "The
pick"): a pair is ranked once its primary's row has `min_rounds` visits;
order = tier (unblocked first; blocked = NHM busy ≥
`radio.scan.blocked_pct`), then rows with a busy reading before rows
without, then the lower worst-visit busy %, then the lower frame score,
then config order. `op` keeps the pick unless the best candidate is in a
better tier (a blocked `op` loses to any unblocked candidate outright),
has a busy reading where `op` has none, or beats `op`'s busy by
`radio.scan.pick_margin_pct` points. There is no noise-floor tie-break on
this path. The proposal is the pair's primary,
so DISC, ChannelPlan and the drone see one channel number. At a derived
receiver width of 40 the pick counts as "measured" — fed to
`HopRanker::set_boot_pick` and logged non-`none` in `scan.log`'s `K` line
— only when some pair is ranked (`any_pair_ranked`).

At the freeze the card parks on `op` with a plain retune (no width
switch) and is already in RX diversity at 40. One-card mode is at 40 from
the start. Width is still desired per-card state
(`RadioFrontend::width()`; a `set_width` on a down card is recorded and
the revive InitWrites at it), and the core keeps its one-shot resync as a
safety net: once no scout thread owns a card and the scan is frozen, any
ready card not at the derived receiver width gets one `set_width` on its
live channel per bring-up ([`gs/src/width_resync.h`](https://github.com/gilankpam/mabur-ground/blob/master/gs/src/width_resync.h)).

Retune cost: FastRetune into an HT40 centre of 54, 102, 118, 151, 159 or
167 takes the slow path; the default set's centres (38, 62, 110, 142) are
spur-free (`docs/findings/2026-09-23-bw40-sweep.md` "Retune cost at
40 MHz").

## In-flight scout: 40-tuned dwells on primaries

Dwells keep the card's 40 MHz tuning (FastRetune) and land on primaries:
NHM busy % covers the whole pair, the frame terms the primary only. The
in-flight `HopRanker` is built over `radio.channels`
([`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md); [`docs/inflight-channel-hop.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/inflight-channel-hop.md) §3); its
evidence is the in-flight dwells and freshness bursts, both on primaries,
with the boot pick only as a tiebreak. Every member is a pair primary
sharing the set's offset, so every ranked channel is a valid hop target:
FastRetune keeps the card's offset, and a secondary half (e.g. 140, the
lower half of member 144's pair) is never in the set. A busy secondary on
the op pair shows up in the verdict window's NHM busy % (the link cards
are 40-tuned too) and, with every rung at 40, as loss and probe failures
on all rungs; the verdict/hop machinery handles it like any other
interference.

## Observability

- ctl.log `ctllog 12`: header `ladder=bw:mcs/ovb:ove,...`.
- fec.log `feclog 3` and probe.log `probelog 3`: a `bw` column after
  `mcs`, so 20/3 and 40/3 do not pool; flightreport groups by (mcs, bw).
- flightreport `BW40` section: time held on 40 MHz rungs, promotes onto them
  vs held past 3 s; "every promote fell straight back" = suspect the secondary.
- scan.log (`scanlog 8`): the D line's `bw` column carries the dwell's
  width and D ends with the dwell's NHM busy % (then a relay rx %); the K
  line's entries carry their own NHM busy and the line ends with
  `pair=<lo>+<hi>` ([`docs/channel-select.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/channel-select.md) "Observability").
- Sideport (v 1): `link.width` (the live derived receiver width, 20 or
  40), `link.ctl.rung.bw`, `link.ctl.ladder[].bw`, `link.rungs[].bw`,
  `link.streams[].rung_bw`; maburtop `mcs3/40`, compact OSD `mcs:3/40`.
- GS stderr: boot logs `maburgs radio: width <w> MHz (<reason>)`, reason
  one of `ladder: no 40 rung`, `ladder: rung <i> bw 40`, `static_bw 40`,
  `static_bw 20` (`derived_width_reason`, [`gs/src/config.h`](https://github.com/gilankpam/mabur-ground/blob/master/gs/src/config.h)). A live
  width flip logs `maburgs link: width <A> -> <B> MHz (ladder set)` plus
  one `maburgs radio: card <N> width <A> -> <B> MHz on ch <C>` line per
  card as it retunes ([`docs/gs-live-config.md`](https://github.com/gilankpam/mabur-ground/blob/master/docs/gs-live-config.md) "Width flip").
- Drone stderr: `maburd radio: A-MPDU ON at mcs3/40 (min_mcs_40 2, max_num 6)`,
  `maburd radio: power table 40 MHz live (mcs5 diff N)`.

## Not measured / later

Per-half attribution in flight: a 40 MHz dwell's NHM busy % already
covers the whole pair, but nothing says which half is dirty; HT40 MCS5; raising the cap; the 149/153 deficit;
the 20-tuned receiver's weak-signal loss (sidestepped
by tuning every GS card 40, not fixed); [`tools/bench/switchloss.py`](https://github.com/gilankpam/mabur-ground/blob/master/tools/bench/switchloss.py) parses
the ctllog 12 `bw:` prefix but still keys rungs by MCS only, so its rate
math is blind to a bw-only rung change.
