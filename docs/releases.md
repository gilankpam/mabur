# Releases, snapshots and PR builds

The drone firmware is built in this repo (`firmware/`) by
`.github/workflows/firmware.yml`, for both boards:
`ssc338q_fpv_openipc-urllc-aio` (RTL8812EU) and
`ssc338q_fpv_emax-wyvern-link-alpha` (RTL8812CU). One mabur commit gives
both images; each image's `maburd` is built from that commit.

## Three levels

| | built on | lands in | who can download | kept |
|---|---|---|---|---|
| **PR build** | a push to a PR that touches `drone/`, `common/`, `bundle/`, `firmware/`, `tools/release.py` or the workflow | the run's artifacts, listed by one bot comment on the PR (edited per push; same-repo PRs only, a fork PR's token cannot comment) | anyone logged in to GitHub | 14 days |
| **Snapshot** | a push to master touching the same paths | the `snapshot` pre-release, replaced each time | anyone | until the next build |
| **Release** | a pushed `v*` tag | a permanent GitHub release, marked Latest | anyone | forever |

A newer push cancels the older build of the same PR or of master; a tag
build is never cancelled.

Files: `mabur-<version>-<board>-nor.tgz` (the sysupgrade image) and
`mabur-<version>-u-boot-ssc338q-nor-padded.bin` (`docs/flash-uboot.md`),
where `<version>` is the tag, `snapshot-<sha8>` or `pr<N>-<sha8>`. A release
also carries the same images under their unversioned names
(`<board>-nor.tgz`, `u-boot-ssc338q-nor-padded.bin`): each board's
`customizer.sh` sets the drone's `upgrade` URL to
`https://github.com/gilankpam/mabur/releases/latest/download/<board>-nor.tgz`.
Snapshots are pre-releases and never Latest, so an online upgrade only
ever takes a release.

## Version rule

Releases are `v0.MINOR.PATCH`, starting at `v0.1.0`.

- **MINOR** when the drone↔GS contract changes: `RC_VERSION`, any `CAP_*`
  constant in `common/include/mabur/rc_proto.h`, the drone parameter table
  in `common/include/mabur/config_params.h` (rows added, removed,
  renamed or reordered), or a removed or renamed drone config key. It
  means "update the ground station with this drone".
- **PATCH** otherwise. It means "drop-in, no GS change".

`tools/release.py check <tag>` enforces the first three: it reads them at
the tag and at the previous `v*` tag and fails when only the patch number
moved over a change. The tag's workflow run runs it before building, so a
mislabelled tag publishes nothing. A removed config key leaves no constant
behind, so the check cannot see it: the PR that removes one says so, and
whoever tags reads the PRs since the last tag.

## Cutting a release

```sh
git tag v0.4.0 <master-sha>
python3 tools/release.py check v0.4.0        # the same check the workflow runs
git push origin v0.4.0
```

If the check fails on GitHub: `git push origin :refs/tags/v0.4.0`, delete
the local tag, and tag the next minor instead. A published release is
never re-tagged; a mistake is fixed by the next number.

The release notes are generated by `tools/release.py notes`: the wire
contract (`RC_VERSION`, the caps, the parameter row count) and what changed
since the previous tag, the mabur, OpenIPC, kernel, devourer and U-Boot commits,
the sha256 of the kernel source, the toolchain and `ipctool` tarballs the
build downloaded, and each file's md5.

## What goes into an image

- **OpenIPC/firmware** at the commit in `firmware/openipc.ref`.
- **The kernel** at the `openipc/linux` commit each board's defconfig pins
  (`BR2_LINUX_KERNEL_CUSTOM_TARBALL_LOCATION`), not OpenIPC's moving
  `sigmastar-infinity6e` branch: that branch's next commit (an infinity6e
  device-tree change to i2c2's pad mux) loses video on about a third of
  boots on these boards.
- Moving either pin is a PR, flown on the bench (ten reboots, each with
  video) before it merges.
- The toolchain and `ipctool` are OpenIPC's rolling downloads, not pinned;
  their sha256 in the notes shows when they moved.
- **devourer** master, resolved once per workflow run (recorded in the
  notes).
- **U-Boot** from `gilankpam/u-boot-sigmastar`, ref `mabur-fastboot`.
- **maburd** from the mabur tree the build runs in
  (`firmware/package/mabur/mabur.mk`, Buildroot `local` site), plus the
  overlay under `firmware/devices/`.

## Building locally

```sh
firmware/builder.sh ssc338q_fpv_openipc-urllc-aio      # on a FHS host
echo 'firmware/builder.sh ssc338q_fpv_openipc-urllc-aio' | nix-shell firmware/shell.nix   # NixOS
```

The image lands in `firmware/openipc/output/images/` with `build-info.txt`
naming what went in. The toolchain the build leaves in
`firmware/openipc/output/host/` is the one `tools/build-arm.sh` uses.
